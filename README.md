# Customer Churn Prediction – MLOps Project

A machine-learning web application that estimates the probability that a telecom customer will leave (churn). It covers the full MLOps cycle: data validation, model comparison, honest evaluation, experiment tracking, an API with a web interface, automated tests, CI, drift monitoring and controlled retraining.

> **Data note.** The data in `data/customer_churn.csv` is **synthetic** (7,000 customers generated by `src/generate_data.py`, with realistic imbalance, noise and missing values). Results on it prove the pipeline works; they do not describe real customers. To use real data, see *Using real data* below.

## Project structure
```text
app/         FastAPI application (/, /predict, /health, /model-info, /monitoring)
frontend/    Web interface (index.html)
src/
  config.py          paths, features, allowed values
  data.py            loading, validation, train/test split
  generate_data.py   synthetic dataset generator
  prepare_telco.py   converts the public Telco churn csv into this format
  train.py           model comparison, calibration, evaluation, MLflow logging
  evaluate.py        evaluation on the held-out test set + charts
  predictor.py       turns one customer into a prediction
  monitoring.py      prediction log, drift (PSI), performance check
  monitor.py         command-line monitoring job
  retrain.py         retrain + promote only if the new model is not worse
models/      churn_model.pkl, metadata.json (metrics, threshold, drift baseline)
reports/     evaluation.json, evaluation.png, feature_importance.png
tests/       test_api.py, test_pipeline.py
.github/     CI workflow + weekly monitoring workflow
Dockerfile
```

## Run it (PyCharm or terminal)
```bash
pip install -r requirements.txt
python src/train.py            # rebuilds the model with your installed library versions (about 1 minute)
python app/main.py             # opens http://127.0.0.1:8000
```
Other commands:
```bash
python src/evaluate.py         # test-set report and charts in reports/
pytest                         # run the tests
python src/monitor.py          # data-drift report -> reports/monitoring.json
python src/retrain.py --force  # retrain; the new model replaces the old one only if not worse
mlflow ui --backend-store-uri sqlite:///mlflow.db
docker build -t churn . && docker run -p 8000:8000 churn
```

## Using real data
1. Download *Telco Customer Churn* (`WA_Fn-UseC_-Telco-Customer-Churn.csv`, about 7,000 customers) from Kaggle.
2. `python src/prepare_telco.py path/to/WA_Fn-UseC_-Telco-Customer-Churn.csv`
3. `python src/train.py` – everything else (API, interface, tests, monitoring) works unchanged.

## How the weaknesses of the first version were fixed
| Weakness | What the project does now |
|---|---|
| Only 20 records | 7,000 records, validated by `data.py` (needs at least 500 rows, checks values, duplicates, missing data) |
| 100% accuracy was suspicious | Honest accuracy on unseen data; the interface and report show that plain accuracy is no better than always predicting "stays", so ROC-AUC, recall and precision are reported |
| Data too easy | Noisy labels, mixed customer types, missing values; `gender` has no effect on churn |
| Test set of 4 customers | 1,400 test customers, plus a bootstrap 95% confidence range for ROC-AUC |
| Evaluation on training data | `evaluate.py` and `train.py` use one shared stratified split; the test part is never used for training, model choice or threshold |
| Extreme probabilities (99.9%) | Pipeline with scaling and one-hot encoding, class weights, and probability calibration; tests fail if the model claims near-certainty |
| No validation | 5-fold cross-validation compares three models; the decision threshold comes from cross-validated predictions |
| Few features | 12 features: demographics, services, contract, billing and payment method |
| No class-imbalance handling | About 26% churners; class weights, PR-AUC, precision/recall and an F1-based threshold |
| Limited monitoring | Every prediction is logged; drift is measured with PSI against the training data; performance checks on newly labelled data; weekly GitHub Actions job; champion/challenger retraining; model versions and metrics in `metadata.json` and MLflow |

## Limitations
- Monitoring and retraining are real and tested, but a production system would also need a scheduler on a server, a database instead of a csv log, alert delivery (email/Slack) and a process for collecting true outcomes.
- The model is trained on synthetic data until you switch to real data.
